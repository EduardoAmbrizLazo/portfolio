Lab 5: Interrupts

Lab Report
Measuring motor speed and direction with a quadrature encoder and interrupts on the STM32.
Author

Eduardo Ambriz Lazo

Published

October 7, 2026

Introduction

In this lab, we once again leveraged the MCU aboard the MicroP’s Dev Board, particularly the STM32L4xx model. The idea was to use interrupts to read a quadrature encoder and measure the speed in rev/s (and by extension RPM) and direction of a 25GA-370 motor spinning in either direction. Reading the encoder with interrupts lets us check that the encoder functions properly and that no pulses are skipped, since the printed speed and the direction logic (CW or CCW) would otherwise glitch. With all of these puzzle pieces, we are able to decode the motor’s encoder and assess the use of interrupts against other strategies like polling. The interrupts worked: we know no pulses were skipped, because skipped pulses made the readings randomly switch direction even when no hardware was changed. That was a problem earlier, but it was quickly patched.

I spent approximately 18 hours on this lab altogether, including familiarizing myself with the idea and a whole lot of debugging.

Design and Testing Methodology

Using SEGGER Embedded Studio, the logic of this lab was contained in a header file and a main file.

There are many timers onboard the MCU but TIM2 has 32 bits and is generally recommended so overflow doesn’t occur and we can leverage its interrupt as long as we use pins PA1 and PA2, which also feature IRQ handlers. These are also great because the MCU datasheet states in section 4 Table 14 that these have an I/O Structure of FT_a which is 5V tolerant.

First, data being read out regarding the bits of calculation and the RPS require 1 kHz refresh in the terminal and computing as specified. Since TIM2 was selected, this is 1 ms and with an IRQHandler we can make it so that when ARR (aka SAMPL, aka sampling frequency) reaches 999 (and we add 1 in the calculations), it triggers an interrupt. This corresponds with 1 second, which is what we want. It should even be compatible with the EXTI IRQ handlers.

The code also notes PPR and is editable to be configured with a motor operating at 150 RPM (408 PPR) though this can be changed. Accounting for the 2 interrupts and the rising and falling edges, we don’t just double this. This was an issue that has been fixed, and it is now an estimated 1632 counts per revolution.

With all this in mind, to calculate RPS, the formula is RPS = count / (cntsperrev*(SAMPL+1) / 1000). We take into account the timer duration (for that PS of RPS) as well as the expected counts per revolution and count which corresponds to observed pulses in both pins (and rising/falling edges).

Now, an important question to ask is why the need for interrupts. Why would interrupts be better than polling or timers?

Implementing polling would theoretically be far easier than interrupts where we simply read the encoder values as prev, do the calculation and we can do a check to do a calculation every time. Polling IS simple to integrate, but it works by counting how many times it reads a value in that 1 second interval. By only relying on digitalRead and timers, we read a value and there is a delay/wait time when a pulse is read. If we’re lucky, it’s fine, but there is a high risk to skip a pulse and be off loop resulting in wildly wrong values or changes in direction where there shouldn’t be. Even if we have a high sampling frequency and low computation, there will still be enough inconsistency for the risk of skipping a pulse to be nonzero.

This also brings up concerns with sampling as a whole with polling and how some speeds can’t be recorded if sampling frequency is not twice or more as the RPS.

Interrupts, theoretically, resolve this because it is not doing the computation all the time and waiting. We only run the computational code when we read something worth processing to trigger an interrupt and thus, processing is more fluid.

In other words, polling has you trapped in a “Data?” while(1) loop which consumes 100% of the CPU’s processing power just for checking. It depends on that loop length for execution and moving on, and it is beholden to the Nyquist-Shannon sampling theorem.

When implemented, we see the theoretical limitations. For polling, even if we use 80 MHz clock (max for the MCU), our cycles are 12.5 ns and in that time, we have to read the IDR, mask the bit, compare, and then go back in basic assembly. Even with severe optimization, it’s 80 MHz divided by let’s say 5 cycles to do this all. That’s 16 million polls. In reality, with the printf() and register saving that number goes considerably down. We get an approximate (from experimentation) of 30-50 kHz which is not great.

The limit for an interrupt is latency and the ISR because the NVIC can handle multiple interrupts and neither affects each other. Latency isn’t a concerning issue but the ISR execution time is how much time is spent in the IRQ handlers. If it takes 100 clock cycles (based on the code below, that’s more than reasonable), then our limit is 80 MHz/(12+100) or 714 kHz. That is FAR better even in the worst case scenario.

Example Calculations and Code

One of the simplest calculations we can do is assuming 408 PPR results in a count of 1632 per revolution. This is because there are two interrupts and a rising and falling edge so we multiply by 4. If we get this the formula ends up as: count/(1632(1000)/1000) where count is 1632 so we get 1 RPS.

On the other hand, let’s say we get a 12V input. In the terminal, we see a real value of around 2.5-2.7. Since the 150 RPM motor is rated for 12V, we expect a value of 150RPM/60 or 2.5 RPS. This is EXACTLY in that margin.

Without these “set in stone” RPS values, we can be a bit more interesting. When trying for 10V we get the following. Since PPR is still 408, we still get that 1632 from the interrupts and such. For 2 rev/s at 10V, there is 3845 pulses for count. Doing the math, count/(1632(1000)/1000) = 2.356. Recalculating this from a motor perspective, using the motor’s rating we expect (10/12)150 RPM = 125 RPM. Divided by 60, this is 2.083. Either way, we expect about that range which was observed experimentally.

Finally, to assess 5V we would expect a pulse count of RPS x PPR x SAMPL and that ends up being 1908. Calculating that from the code, we get 1908/1632 or 1.169. That matches our experimental value very closely.

Results and Discussion

The overall design and construction was successful, as confirmed via the debug terminal and the successful upload of the solution to the MCU. I was able to accomplish all tasks outlined at the beginning of this lab report and even handle the direction of the motor.

Conclusion

The design successfully measured the speed and direction of the motor using interrupts on a quadrature encoder. I learned a lot about configuring interrupts and the NVIC, about communicating with the MCU using a reference manual and datasheet, and about why interrupts beat polling when no pulse can be missed.
