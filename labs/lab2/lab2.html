Lab 2: Multiplexed Seven Segment Display

Lab Report
Multiplexing a dual seven segment display and scanning a 4x4 keypad with transistor-driven rows.
Author

Eduardo Ambriz Lazo

Published

September 15, 2026

Introduction

In this lab, we built on the single seven segment display from Lab 1 and used the FPGA aboard the MicroP’s Dev Board to drive a dual seven segment display. Multiplexing logic selects which DIP switch input is shown on which digit and flashes the two hex digits fast enough that the flicker is undetectable to the human eye. The decoder and counter modules are identical to Lab 1; a new top-level module uses the parameterized counter to flash the digits and to select the right DIP switch and digit (i.e., the common anode of the dual seven segment display). Multiplexing lets us control two digits with just 9 pins. Using the counter module, we divide the internal 48 MHz clock by ~18’b0 (all ones, so the counter runs through its full 18-bit range), resulting in a clock of ~90 Hz (due to toggling), which is indeed sufficient.

This lab also included building a scanning module so a scanning signal is displayed at ~2 Hz on the internal LEDs when buttons on a keypad are pressed. The idea is that each row runs at a slightly different offset clock cycle, and pressing all 4 columns in conjunction results in a synchronized blinking. Furthermore, both designs took advantage of the physics of PNP and NPN transistors so the FPGA pins never drain more than 8 mA while still delivering sufficient current.

I spent approximately 15 hours on this lab altogether, including familiarizing myself with the idea and a whole lot of debugging.

Design and Testing Methodology

The overall logic was stored in four modules, where the top module called on the counter, decoder, and scanner submodules. It also included the assign logic prescribing which digit to select (based on the count declared in the top module) and assigned the LEDs to be the inverse of the column inputs in the scanner. The scanner submodule contains a counter of its own (targeting that 2 Hz) and scans a 4 x 4 keypad by setting a 4-bit row vector HIGH one bit at a time. As previously stated, the parameterized clock divider in the top module was 18 bits, whereas here it increases to 25 bits (a lower frequency, naturally).

logic int_osc;
// Internal high-speed oscillator 48 MHz
HSOSC hf_osc (.CLKHFPU (1'b1), .CLKHFEN (1'b1), .CLKHF(int_osc));

// Leverage winker to get the desired Hz so the digits blink fast enough to not be seen
logic [17:0] displayCount;
winker #(18, ~18'b0) display(.int_osc (int_osc), .nreset (nreset), .en (1'b1), .count (displayCount));

logic [3:0] sActive;
assign sActive = ~displayCount[17] ? sRight : sLeft; // Multiplexer

decoder decode(.s (sActive), .seg (seg)); // calls on decoder module
scanner scan(.int_osc (int_osc), .nreset (nreset), .en (1'b1), .row (row));

assign digit[0] = ~displayCount[17];
assign digit[1] = displayCount[17];
assign led = ~col;
NoteScanner Bit Shift Logic and Parameterization 
module scanner #(
    parameter WIDTH = 25,
    parameter MAX = ~25'b0
)(
    input  logic int_osc, nreset, en,
    output logic [3:0] row
);
    logic [WIDTH-1:0] keypadCount;
    winker #(WIDTH, MAX) keypad(.int_osc (int_osc), .nreset (nreset), .en (en), .count (keypadCount));
    assign row = 1'b1 << (keypadCount[WIDTH-1:WIDTH-2]); // For the sake of parameterization
endmodule

For further elaboration, the scanner module was parameterized so the clock division can be decreased in simulation, which lets an internally generated clock exhibit the expected waveforms.

Block Diagram

The block diagram in Figure 1 demonstrates the overall architecture of the design. The top-level module lab2_ea includes three submodules: the winker/counter (winker), which is parameterized to provide a range of frequencies to the top module or the scanner; the scanner (scanner), which cycles which bit of the [3:0] row output vector (fed into the keypad) is HIGH; and the 7-segment display logic module (decoder). Additionally, HSOSC is leveraged for an internal 48 MHz clock.

Schematic

Figure 2 shows the electrical layout of the design. Because driving every segment at 10 mA is strenuous (especially if we consider a case where both digits display 8), 150 \(\Omega\) was the appropriate value per the equation \(R_{seg} = (3.3\,\text{V} - 2\,\text{V}) / 10\,\text{mA}\), making 150 \(\Omega\) our ideal choice.

The transistors and the resistor values associated with the keypad scanner were also paramount. First, the display was multiplexed by having two independent 2N3906 PNP transistors control the common anode of each digit (specifically, the collector pin of the transistor). These transistors are configured to saturate when the FPGA pin (connected to the base) reads LOW. The emitter is simply connected to +3.3 V.

Each of the four keypad rows uses an NPN setup. Following the E155 site instructions, the emitter is connected to the FPGA ground, and the base is connected to an FPGA pin (the row outputs) through a resistor (\(R_{base}\)). The collector is wired to the rows of the keypad as shown in Figure 2, and the columns are wired both to the FPGA as column inputs and to +3.3 V via a 1 k\(\Omega\) pull-up resistor. The value of this resistor is somewhat arbitrary and should just be a decent value for a pull-up. However, it does inform the value of \(R_{base}\). The equation is \(R_{base} = (3.3\,\text{V} - 0.7\,\text{V}) / I_{base}\), where 0.7 V is the base-emitter voltage drop and \(I_{base}\) is expected to be \(I_{collector}/10\), or 0.33 mA. This ultimately yields a value of 7.8 k\(\Omega\), though a 2.2 k\(\Omega\) resistor serves our purpose of saturating the transistor just fine.

Results and Discussion

The overall design and construction was successful, as confirmed via simulation and through the physical circuitry. I was able to accomplish all tasks outlined at the beginning of this lab report and utilize some interesting code and pin assignment workarounds. Overall, the results are as expected, even with a few roadblocks in testbench logic and with pins being assigned incorrectly or not reading values.

// Module 2: Time-Multiplexed Dual Seven-Segment Display Controller
module seg7_mux_top (
    input  logic       clk,      // System clock
    input  logic       rst,      // Active-high reset
    input  logic [3:0] in0,      // First 4-bit BCD input
    input  logic [3:0] in1,      // Second 4-bit BCD input
    output logic [6:0] seg_out,  // Cathode segment drive outputs (shared)
    output logic [1:0] anodes    // Common Anodes control (active-low)
);
    // Clock Divider / Multiplexing Toggle Flag
    // For hardware implementation, set counter size to refresh around ~1 kHz to prevent flicker
    logic [15:0] refresh_counter;
    logic        select_reg;

    always_ff @(posedge clk or posedge rst) begin
        if (rst) begin
            refresh_counter <= '0;
            select_reg      <= 1'b0;
        end else begin
            refresh_counter <= refresh_counter + 1'b1;
            select_reg      <= refresh_counter[15]; // Toggles active display
        end
    end

    // 2-to-1 Multiplexer for BCD inputs
    logic [3:0] current_bcd;
    assign current_bcd = select_reg ? in1 : in0;

    // Single Decoder Instance
    seg7_decoder u_decoder (
        .bcd (current_bcd),
        .seg (seg_out)
    );

    // Active-Low Anode Controller (Enable one display at a time)
    // anodes[0] drives Display 0, anodes[1] drives Display 1
    assign anodes = select_reg ? 2'b10 : 2'b01;
endmodule

    // Instantiate provided 7-segment decoder
    decoder decoder_inst (
        .s(current_in),
        .seg(decoded_seg)
    );

    // Demux / Register output: Hold and display the decoded bits for each segment
    always_ff @(posedge clk or negedge reset) begin
        if (!reset) begin
            seg0 <= 7'b1111111; // Off state for common anode
            seg1 <= 7'b1111111;
        end else begin
            if (mux_sel) begin
                seg1 <= decoded_seg;
            end else begin
                seg0 <= decoded_seg;
            end
        end
    end

For clarity, the two prompts were as follows:

  1. Write SystemVerilog HDL to time multiplex a single seven segment decoder (that decodes from four bits to a common anode seven segment display) to decode two sets of input bits and drive two sets of seven output bits.
  2. The same prompt, plus: Use the seven segment decoder and oscillator provided in the attached files.

I prompted Gemini via the Harvey Mudd license (so my data would not be used to train the AI), and I was presented with the first block of code in this section. Notably, it is quite dense and has some distinct deviations from my approach, including unclear signal names, a lack of parameterization (which wasn’t specified but is definitely valuable for testbenches), and only a single, VERY SHORT testbench that doesn’t check things thoroughly. It didn’t synthesize the first time because of a strange misspelling in the always_comb statement. I also tried pasting all of it into a single .sv file (which synthesized successfully), though I suspect separate files would be preferred.

When I prompted Gemini in a new tab with the files attached, it did remarkably well at calling my modules and organizing the signals, which genuinely surprised me since I thought it would ignore the files or make things up. This time around, it used a demux block, which is essentially the sActive mux logic with some strange reset cases.

Figure 5 shows a screenshot of the synthesis and the warnings that appeared. Some are minor, but the “clk” warning made me realize it didn’t leverage the internal oscillator that my counter module depends on. It also preferred clk as a signal name over my consistent int_osc. Overall, AI seems to be even stronger when it has files to build on, but it lacks some of the creative decisions I made while designing the logic.
